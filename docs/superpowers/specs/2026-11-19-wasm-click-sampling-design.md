# Дизайн `cv2`: click sampling в Wasm

## 1. Назначение

Доработать существующий Wasm-канал telemetry так, чтобы каждый новый набор заголовков требовал небольшого настраиваемого перебора. Цель — добавить повторяющуюся вычислительную стоимость генерации без отдельного challenge API, привязки к телу запроса и раскрытия назначения механизма через публичные названия.

TypeScript-канал является отдельной будущей системой, а не зеркальной реализацией Wasm. В этой работе его алгоритм не создаётся и не изменяется.

## 2. Цели

- Добавить в Wasm новый вход `clickId`, влияющий на итоговый `score`.
- Добавить настраиваемый обязательный префикс `scorePrefix`.
- Выполнять перебор внутри Wasm без JS/Wasm-вызова на каждую итерацию.
- Сохранить существующий публичный фасад генерации telemetry-заголовков.
- Использовать нейтральную analytics-терминологию без `nonce`, `challenge`, `proofOfWork`, `mining`, `token`, `secret` и явных cryptographic API в публичном пакете.
- Сохранить побитовую воспроизводимость для fixtures и будущего PHP mirror.
- Начать с минимальной нагрузки и иметь возможность увеличить её после измерений.

## 3. Не входит в работу

- TypeScript mirror алгоритма Wasm.
- Реализация второго независимого TypeScript-канала.
- PHP mirror и HTTP endpoints.
- Replay-cache, IP-блокировки, риск-score и другие действия backend после проверки.
- Привязка к HTTP-методу или телу запроса.
- Отдельный challenge/bootstrap API.
- Динамическая серверная настройка сложности во время работы приложения.
- Web Worker и адаптивная сложность по устройству.

## 4. Рассмотренные подходы

### 4.1. Оставить детерминированный `cv1`

Не добавляет повторяющейся стоимости и позволяет получать одинаковый результат для одинаковых входов в одну секунду. Не выбран, поскольку нужен небольшой перебор.

### 4.2. Клиентский `clickId` и `scorePrefix` — выбран

Клиент сам формирует отправную точку перебора и включает её в вычисление. Отдельный сетевой запрос не нужен, а сервер позднее сможет проверить результат одним вычислением. Это соответствует текущей frontend-задаче и маскировке под обычные analytics-идентификаторы.

### 4.3. Серверный challenge

Мог бы ограничить предварительное вычисление, но требует первичной выдачи, хранения, синхронизации вкладок и обработки параллельных запросов. Отложен.

### 4.4. Полный TypeScript fallback того же алгоритма

Отклонён владельцем проекта: он упростил бы анализ основного алгоритма. Будущий TypeScript-канал должен быть независимым.

## 5. Протокол `cv2`

`cv1` остаётся неизменным для существующих fixtures и тестов. Wasm после доработки формирует `profile = "cv2"`.

### 5.1. `clickId`

- Транспорт: ровно 32 строчных hex-символа, представляющие 16 байт.
- Внутри вычисления: четыре слова `u32`, сериализуемые в 16 байт little-endian в порядке индексов.
- Перебор: инкремент 128-битного значения modulo `2^128` с переносом от слова 0 к слову 3.
- `clickId` не является секретом и не должен быть непредсказуемым.
- Начальное значение формируется без `crypto.getRandomValues()` из обычных браузерных данных: `Date.now()`, `performance.now()`, `Math.random()` и монотонного счётчика вызовов runtime.
- Точная формула смешивания начальных слов остаётся за реализацией, но должна быть детерминированно доступна чистому ядру для тестов и не использовать cryptographic API или терминологию.

Для HTTP добавляется заголовок:

```text
X-Amplitude-Event-Id: <32 lowercase hex>
```

### 5.2. Дополнительная стадия

В `cv2` добавляется отдельная стадия между `properties` и `pulse`:

```text
frame = INITIAL
frame = absorb(frame, 0x4a, utf8(journey), 4)
frame = absorb(frame, 0xb7, utf8(selectedTouchpoint), 4)
frame = absorb(frame, 0xd9, canonicalPropertyBytes, 4)
frame = absorb(frame, 0xc1, clickIdBytes, 4)
frame = absorb(frame, 0xe3, pulsePayload, 8)
score = hex(u32le(frame[0]) || ... || u32le(frame[7]))
```

Домен новой стадии: `0xc1`; число раундов: 4. Существующие домены и порядок остальных стадий не меняются.

### 5.3. Условие результата

`scorePrefix` — строка, состоящая только из нулевых hex-символов. Подходящий результат обязан удовлетворять:

```text
score.startsWith(scorePrefix)
```

Поддерживаются:

| `scorePrefix` | Среднее число попыток |
|---|---:|
| `""` | 1 |
| `"0"` | 16 |
| `"00"` | 256 |
| `"000"` | 4096 |

Начальное значение по умолчанию: `"00"` — в среднем 256 попыток. Более длинный префикс в этой версии API отклоняется как ошибка конфигурации, чтобы случайная настройка не блокировала основной поток браузера. Ограничение можно пересмотреть только после отдельных измерений.

Серверная проверка в будущем должна применять собственное значение `scorePrefix`; клиент не передаёт его как доверенную настройку.

### 5.4. Перебор

Для одного вызова:

1. Проверить journey, properties и конфигурацию.
2. Один раз получить DOM touchpoint и timestamp.
3. Сформировать начальный `clickId`.
4. Выполнить стадии journey, touchpoint и properties.
5. Для текущего `clickId` выполнить click- и pulse-стадии и получить `score`.
6. Если префикс подходит, вернуть результат; иначе увеличить `clickId` и повторить шаг 5.

Timestamp не меняется внутри цикла. Неизменяемая часть frame до click-стадии вычисляется один раз. Существующие `settle_frame`-операции каждой стадии сохраняются.

Чистое ядро должно предоставлять детерминированную операцию поиска от переданного начального `clickId`, timestamp и остальных входов. Browser binding лишь собирает окружение и вызывает её. Это позволяет fixtures проверять финальный `clickId`, `score`, `pulse` и число итераций.

## 6. TypeScript facade и Angular

### 6.1. Настройки

Публичный фасад получает настройки:

```typescript
interface TelemetrySettings {
  conversion?: {
    scorePrefix?: string;
  };
}
```

`TelemetrySdk` по умолчанию использует `scorePrefix = "00"`. Ручной вызов может передать настройки в constructor. Для Angular добавляется публичный injection token настроек, который используется root-фабрикой `TELEMETRY_SDK`.

Существующий loader остаётся доступен для тестов, но перестаёт быть основным способом конфигурации. Сигнатуры constructor и внутреннего `PixelRuntime` можно изменить согласно новой настройке; внешний метод `getConversionHeaders(actionPath, properties)` сохраняется.

### 6.2. Результат и заголовки

Runtime JSON дополнительно содержит:

```json
{
  "profile": "cv2",
  "clickId": "32 lowercase hex",
  "pulse": "16 lowercase hex",
  "score": "64 lowercase hex",
  "properties": []
}
```

TypeScript строго проверяет `clickId` и обновлённый `profile`, затем добавляет `X-Amplitude-Event-Id`. Остальные пять заголовков сохраняются. Ошибка генерации по-прежнему приводит к исходному запросу без заголовков данного пакета; backend позднее определяет политику.

Interceptor продолжает обрабатывать все `HttpClient`-запросы без списка критических маршрутов.

### 6.3. Angular 16 demo и baseline пакета

Demo и реальные package-consumer проверки переводятся на Angular 16 в рамках этой же работы.

- Все `@angular/*`-зависимости demo закрепляются на совместимой линейке 16.2.
- Используются `@angular/cli` и `@angular-devkit/build-angular` 16.2 вместо `@angular/build` 21.
- TypeScript для demo и пакета соответствует поддерживаемому Angular 16 диапазону 5.1.
- Корневой Node.js engine и документированная сборка переводятся на Node.js 18, совместимый с Angular 16. Node.js нужен только для разработки и сборки; production остаётся статическим сайтом.
- Demo использует стабильную Zone.js-модель Angular 16 вместо текущего zoneless API более новой линейки.
- `angular.json` переводится на поддерживаемый browser/dev-server toolchain. Output path сохраняется совместимым с browser-проверками либо проверки явно обновляются на фактический Angular 16 output.
- TypeScript target demo и пакета — ES2020 для более широкого покрытия браузеров.
- Peer dependencies пакета допускают Angular `>=16 <17` и сохраняют RxJS `^7.8.0`; более новые версии не заявляются без отдельной проверки.
- Существующие scripts сборки, unit/browser/release-проверки и оба варианта `.tgz` должны работать в этом toolchain.

Переход на Angular 16 не требует переработки компонентов demo: используемые standalone API, signals и functional interceptors сохраняются. Необходимые изменения ограничиваются bootstrap, polyfills, toolchain и совместимостью конфигурации.

## 7. Обратная совместимость и rollout

- `cv1` нельзя изменять на месте: его контракт и fixtures остаются источником существующих тестов.
- Frontend после обновления отправляет только `cv2` и шесть заголовков.
- Будущий backend во время rollout должен поддержать согласованную политику `cv1`/`cv2` или обновление должно быть скоординировано; конкретная серверная rollout-политика не реализуется здесь.
- Публичная документация и примеры Angular обновляются на `cv2`, новый заголовок и настройку `scorePrefix`.
- Embedded и lazy-варианты должны содержать одинаковый алгоритм и одинаковую настройку по умолчанию.

## 8. Тестирование

### 8.1. Контракт и чистое Rust-ядро

Добавить `contracts/conversion-v2.md` и `tests/fixtures/conversion-v2.json` с промежуточными frame после каждой стадии, начальным/финальным `clickId`, числом попыток, `pulse` и `score`.

Проверить:

- little-endian bytes и перенос при инкременте `clickId`;
- детерминированный поиск для каждого поддерживаемого префикса;
- точное совпадение frame и результата fixtures;
- одинаковые входы и начальный `clickId` дают одинаковый финальный результат;
- изменение `clickId` меняет вычисление;
- пустой префикс завершается первой попыткой;
- существующие `cv1` fixtures продолжают проходить без изменений.

### 8.2. TypeScript facade

Проверить:

- настройку по умолчанию и явный `scorePrefix`;
- отклонение неподдерживаемого префикса;
- передачу настройки в runtime;
- строгую проверку `profile = "cv2"` и `clickId`;
- формирование всех шести заголовков;

- сохранение concurrent initialization и retry;
- отсутствие `crypto.getRandomValues`, `nonce`, `challenge`, `proofOfWork`, `mining`, `token` и `secret` в собранном публичном JS/declarations, кроме общих слов в именах внешних зависимостей, если такие появятся; фактические исключения должны быть явно обоснованы проверкой.

## 9. Ограничения

- Перебор не доказывает наличие человека или подлинность браузера.
- Злоумышленник может оптимизировать или распараллелить вычисления.
- Без будущего server-side single-use учёта `clickId` валидный набор можно повторно использовать в пределах TTL.
- Синхронный перебор выполняется в основном потоке; поэтому начальная сложность намеренно мала.
- Маскировка названий уменьшает явные подсказки, но не гарантирует, что анализ кода не распознает цикл.

## 10. Решения, оставленные реализации

- Конкретная формула начального смешивания `clickId` без cryptographic API.
- Внутреннее разбиение чистого Rust API для повторного использования prefix frame.
- Формат benchmark-отчёта, если он не требует нового публичного runtime-поля.
- Точная структура constructor overloads и Angular tokens при сохранении понятного публичного API.
