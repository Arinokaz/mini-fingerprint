# Идеи для развития после базовой реализации

## 1. Назначение документа

Документ сохраняет идеи реагирования на подозрительные запросы и дальнейшего развития системы. Перечисленные здесь решения не являются частью контрактов `cv1`/`cv2`; реализация frontend `cv2` не означает наличие backend-политики и не должна подменять её наблюдениями.

Текущий порядок работ:

1. Реализовать фронтенд-генерацию двух независимых наборов telemetry-заголовков: обязательного лёгкого TypeScript и дополнительного тяжёлого Wasm.
2. Реализовать приём и независимую проверку обоих наборов на backend.
3. Добавить наблюдение и внутреннюю регистрацию различий между ожидаемым и фактическим состоянием заголовков.
4. Только после накопления наблюдений выбирать и настраивать меры реагирования.

TypeScript не должен повторять алгоритм Wasm. Это отдельный канал с собственными вычислениями, а не fallback-копия основного алгоритма.

## 2. Исходная классификация запросов

Для последующего наблюдения предполагается различать следующие состояния:

| TypeScript | Wasm | Предварительная интерпретация |
|---|---|---|
| Валиден | Валиден | Ожидаемый полный набор заголовков |
| Валиден | Отсутствует | Запрос потенциально требует дополнительного наблюдения |
| Валиден | Невалиден | Ошибка вычисления, несовместимость версий или возможная подделка |
| Отсутствует | Любой | Запрос вне ожидаемой frontend-схемы |
| Невалиден | Любой | Ошибка вычисления, несовместимость версий или возможная подделка |

Классификация не должна автоматически означать злонамеренность клиента. Отсутствие или повреждение заголовков может быть связано с CSP, браузерными расширениями, старой версией приложения, кешем, ошибкой деплоя или особенностями устройства.

## 3. Регистрация TypeScript-only

Если пришёл валидный TypeScript-набор без Wasm-заголовков, можно сохранять внутренний сигнал риска для IP и, если появится соответствующий серверный контекст, для анонимной сессии.

На первом этапе достаточно регистрировать событие без блокировки и без изменения внешнего HTTP-ответа. Полезные поля наблюдения:

- время и внутренний request ID;
- нормализованный маршрут и HTTP-метод;
- версии профилей TypeScript и Wasm;
- состояние каждого набора: valid, missing, malformed, mismatch, unsupported;
- IP или его защищённое производное представление согласно политике хранения;
- обобщённые сведения User-Agent;
- внутренняя причина классификации без раскрытия её клиенту.

Пароли, тела запросов, полные наборы заголовков и другие чувствительные данные в такие записи не включать. Сроки хранения IP и связанных идентификаторов должны быть ограничены отдельной политикой.

## 4. Доступность Wasm, CSP и User-Agent

### 4.1. Общая конфигурация сайта и клиентские исключения

CSP задаётся сервером через HTTP-ответ или страницей через `meta`, а не индивидуально обычным посетителем. Если production CSP запрещает компиляцию Wasm, проблема может затрагивать всех посетителей соответствующей страницы. Разные CSP на dev/staging/production или на отдельных страницах могут объяснять различия между окружениями.

Текущий Wasm встроен в JavaScript через base64, поэтому отдельный сетевой `.wasm`-запрос, MIME-тип и `connect-src` для него не используются. Проверять нужно разрешение CSP на компиляцию и выполнение Wasm через `script-src` в фактическом production-ответе.

Индивидуальные клиентские исключения возможны, но не должны считаться нормой для современного браузера:

- очень старый браузер без поддержки Wasm;
- старый или специфический in-app WebView;
- корпоративно управляемый браузер с ограничениями;
- изменённые настройки или расширения;
- редкая ошибка инициализации из-за ресурсов устройства.

Если Wasm работает в production smoke-тесте, CSP настроена корректно и нет массовых ошибок релиза, ожидаемое состояние для подавляющего большинства современных браузеров — наличие Wasm-заголовков. Массовый переход на TypeScript-only сразу после деплоя сначала должен рассматриваться как возможная проблема CSP или релиза, а не как атака.

### 4.2. User-Agent как вспомогательный сигнал

Можно исследовать сочетание свежего User-Agent и постоянного отсутствия Wasm как более заметную аномалию. Злоумышленник, стремящийся слиться с обычным трафиком, вероятнее будет использовать популярные современные User-Agent, а не намеренно старые версии браузеров и устройств. Пока правило не раскрыто, сочетание свежего Chrome и TypeScript-only может быть полезным индикатором того, что был воспроизведён только лёгкий TypeScript-канал.

Предварительные веса наблюдений:

| Наблюдение | Предварительная интерпретация |
|---|---|
| Старый UA + TypeScript-only | Слабая аномалия; возможна реальная несовместимость |
| Свежий Chrome + единичный TypeScript-only | Небольшая аномалия |
| Свежий Chrome + постоянный TypeScript-only | Более заметная аномалия |
| Один IP, много аккаунтов, свежие UA и только TypeScript | Сильная аномалия |
| Массовый TypeScript-only у многих пользователей после деплоя | Сначала проверить CSP и релиз |
| TypeScript и Wasm валидны | Ожидаемое состояние |

Дополнительно полезно различать единичное исчезновение Wasm в сессии и сотни последовательных TypeScript-only запросов. После раскрытия правила злоумышленник может начать подставлять старые UA, поэтому долговременная ценность сигнала зависит от сочетания с другими наблюдениями.

Ограничения:

- User-Agent легко подменяется и не доказывает возможности окружения;
- современный браузер может находиться под enterprise-политикой, работать в WebView или иметь изменённые настройки;
- User-Agent может быть сокращён или обобщён;
- одно сочетание User-Agent и TypeScript-only не должно приводить к блокировке.

Предполагаемое применение — агрегированная аналитика и один из нескольких сигналов риска, а не самостоятельное правило отклонения.

## 5. Идеи реагирования после накопления наблюдений

Возможные меры, требующие отдельной оценки перед внедрением:

- временный риск-score с TTL вместо постоянной метки клиента;
- более строгие лимиты частоты и параллельности для TypeScript-only;
- ограничение числа аккаунтов или чувствительных операций для сессии/IP с повышенным риском;
- дополнительная проверка или WAF-наблюдение при сочетании нескольких аномалий;
- разные веса для missing, malformed и mismatch;
- эскалация от короткой задержки или временного ограничения к более продолжительной блокировке при повторных подтверждённых нарушениях;
- автоматическое снижение риска после периода нормальной активности.

Конкретные пороги и сценарии должны опираться на измеренную частоту ложных срабатываний. Наружу во всех случаях отклонения сохранять одинаковый generic-ответ без причины.

## 6. IP-блокировки: отложенные вопросы

Суточная блокировка IP за неверный результат может увеличить стоимость исследования для злоумышленника, но требует осторожности из-за NAT, CGNAT, корпоративных сетей и общего Wi-Fi. Один внешний IP может обслуживать много независимых пользователей.

Перед внедрением рассмотреть:

- отделение отклонения запроса от наказания IP;
- счётчик повторных mismatch вместо блокировки после первой ошибки;
- короткую начальную блокировку с эскалацией при продолжении;
- отдельную политику для отсутствующих заголовков и для формально корректных, но неверных значений;
- период observation-only перед включением наказаний;
- поведение при одновременном обновлении frontend и backend;
- правила ручного и автоматического снятия ошибочной блокировки.

Client IP должен определяться только через доверенную proxy-цепочку. Нельзя безусловно доверять клиентскому `X-Forwarded-For`, иначе возможны подделка источника и блокировка чужих адресов. Для IPv6 отдельно сравнить блокировку `/128` и `/64` по риску обхода и collateral damage.

## 7. Нагрузка двух вычислительных каналов

Два тяжёлых перебора на каждый API-запрос могут создать заметную задержку, нагрузку на CPU и расход батареи. TypeScript-перебор на слабом устройстве может оказаться существенно медленнее Wasm.

До изменения вычислительной схемы измерить отдельно и совместно:

- median, p95 и p99 времени генерации заголовков;
- стоимость одной итерации и полного перебора;
- поведение на слабых мобильных устройствах;
- влияние на обычные API-запросы, поскольку telemetry применяется ко всем запросам приложения;
- параллельные запросы и работу нескольких вкладок.

До получения таких измерений TypeScript остаётся лёгким каналом без собственного тяжёлого перебора. Если TypeScript-only разрешён, его более низкая вычислительная стоимость компенсируется пока только регистрацией риска; любые дополнительные ограничения относятся к последующим этапам.

## 8. Граница текущего этапа

Сейчас не требуются:

- динамические правила блокировки;
- постоянные метки пользователей;
- отдельный challenge API;
- привязка вычисления к телу запроса;
- выбор маршрутов, на которых telemetry считается критичной;
- адаптивная сложность по результатам риска.

Сначала необходимо получить стабильную генерацию заголовков, зеркальную серверную проверку и достоверные наблюдения. Политику реагирования затем можно развивать независимо, не меняя базовый клиентский протокол без необходимости.
